mattpocock-skills v1.3.1 · sozinho

Como funcionam as skills do Matt Pocock

Um passeio pelo plugin inteiro, sem aicf e sem Superpowers: o que cada skill faz, em que ordem elas se encadeiam, que arquivos deixam no repositório e onde a decisão fica com você. No fim, duas seções o comparam com o aicf.

1. A ideia

O Matt abre o README com uma crítica: frameworks como GSD, BMAD e Spec-Kit "são donos do processo" e, com isso, tiram o controle de quem usa. A proposta dele é o oposto: skills pequenas, fáceis de adaptar e combináveis, cada uma com um trabalho só. Não existe um orquestrador central que conduz você de ponta a ponta; existe um mapa (a skill /ask-matt) e você decide o próximo passo.

Cada skill existe para consertar um modo de falha que ele observa em agentes de código:

Modo de falhaCausaConserto
O agente não fez o que eu queriaDesalinhamento: ninguém sabe exatamente o que querEntrevista antes de codar: /grill-with-docs, /grill-me
O agente é prolixo demaisFalta linguagem comum do domínioGLOSSARY.md mantido durante a entrevista (/domain-modeling)
O código não funcionaFalta feedback sobre o código que rodaCiclo vermelho → verde (/tdd) e depuração com loop (/diagnosing-bugs)
Viramos uma bola de lamaAgentes aceleram a entropia do códigoMódulos profundos (/codebase-design, /improve-codebase-architecture)

2. Dois tipos de skill

A divisão que organiza o plugin inteiro é quem pode disparar a skill. Ela é controlada por um campo no cabeçalho do SKILL.md: disable-model-invocation: true faz o Claude Code esconder a skill do agente, e só você consegue chamá-la digitando o comando.

você invoca Orquestram

Só rodam quando você digita. São os passos do fluxo: /grill-with-docs, /to-spec, /to-tickets, /implement, /implement-spec, /triage, /wayfinder, /retro, /handoff, /ask-matt, /setup-matt-pocock-skills…

agente também invoca Guardam a disciplina

O agente as carrega sozinho quando a tarefa casa com a descrição, ou outra skill as chama. São o "como fazer bem": /grilling, /tdd, /code-review, /diagnosing-bugs, /domain-modeling, /codebase-design, /prototype, /research, /pr, /wizard.

Regra de composição: uma skill de usuário pode chamar skills de modelo, mas nunca outra skill de usuário. Por isso o fluxo não se encadeia sozinho: /to-spec não chama /to-tickets, e nada chama /implement. Quem passa de um passo ao outro é você.

Várias skills de usuário são quase só um ponteiro. O SKILL.md inteiro do /grill-with-docs é uma linha: "chame a skill grilling e a skill domain-modeling". O /grill-me chama só grilling. A lógica mora nas skills de modelo; as de usuário dão nome a uma combinação.

Como aparece na sua sessãoNa lista de skills que o agente enxerga só aparecem as de modelo (com o prefixo mattpocock-skills:). As de usuário continuam disponíveis como comandos com barra; você as vê ao digitar / no Claude Code.

3. Instalar e configurar

Há dois jeitos de instalar, e o Matt pede que você escolha um só (os dois juntos duplicam cada skill):

  • Plugin do Claude Code (/plugin install mattpocock-skills): pacote gerenciado, somente leitura, que se atualiza quando ele publica. É o seu caso.
  • skills.sh (npx skills@latest add mattpocock/skills): copia os arquivos para dentro do seu repositório, editáveis, e só atualiza quando você pede.

O /setup-matt-pocock-skills, uma vez por repositório

As skills de engenharia leem configuração do repositório, e é este comando que a escreve. Ele explora o repositório (remote do git, CLAUDE.md/AGENTS.md, GLOSSARY.md, docs/adr/, .scratch/, sinais de monorepo), mostra o que achou e faz no máximo três perguntas, sempre com a resposta recomendada na frente:

A · Tracker
Onde moram as issues. GitHub (via gh), GitLab (via glab), markdown local em .scratch/, ou outro descrito em prosa (Jira, Linear).
B · Labels
Só se o /triage estiver instalado: manter os cinco labels padrão (needs-triage, needs-info, ready-for-agent, ready-for-human, wontfix) ou mapear para os nomes que o seu tracker já usa.
C · Domínio
Só se houver sinal de monorepo: um GLOSSARY.md na raiz (o padrão) ou um GLOSSARY-MAP.md apontando um glossário por contexto.

Ele mostra o rascunho, deixa você editar e então escreve:

CLAUDE.md                     ← ganha um bloco "## Agent skills" com ponteiros
docs/agents/issue-tracker.md  ← como criar, ler, comentar e fechar issues
docs/agents/triage-labels.md  ← mapeamento de labels (só com /triage)
docs/agents/domain.md         ← onde está o glossário e as regras de leitura

Esses arquivos são a "porta" entre as skills e o seu projeto. O issue-tracker.md, por exemplo, traduz frases genéricas das skills ("publique no tracker", "busque o ticket") em comandos concretos: gh issue create no GitHub, ou "crie um arquivo em .scratch/<feature>/" no modo local. Depois do setup, você pode editar esses arquivos à mão; rodar o setup de novo só é preciso para trocar de tracker.

O GLOSSARY.md e o docs/adr/ não são criados no setup. Eles nascem sob demanda, quando o primeiro termo for resolvido ou a primeira decisão merecer registro.

4. O fluxo principal: da ideia ao código entregue

O /ask-matt chama isto de main flow: o caminho que a maior parte do trabalho percorre. Há dois desvios opcionais: protótipo, quando uma pergunta só se responde rodando código, e o tamanho da obra, que decide entre implementar direto ou quebrar em tickets.

flowchart TD
  A["/grill-with-docs: entrevista + glossário + ADR"] --> B{"Alguma pergunta precisa de código para responder?"}
  B -- sim --> P["/handoff → /prototype → /handoff de volta"]
  P --> C
  B -- não --> C{"Cabe numa sessão?"}
  C -- não --> S["/to-spec: spec no tracker"]
  S --> T["/to-tickets: fatias com bloqueios"]
  T --> I1["/implement por ticket (/clear entre eles)"]
  T --> I2["/implement-spec: todos em paralelo"]
  C -- sim --> I0["/implement: na mesma sessão"]
  I0 --> R["/tdd + /code-review: dentro do implement"]
  I1 --> R
  I2 --> R
  R --> PR["/pr (se for PR)"]
  PR --> RE["/retro: melhora o ambiente"]
1

/grill-with-docs você invoca

A entrevista. O agente monta uma árvore de decisões (cada decisão abre as decisões que dependem dela) e trabalha em rodadas. Em cada rodada pergunta toda a fronteira: as decisões cujos pré-requisitos já estão resolvidos. Cada pergunta vem numerada e com a resposta que ele recomenda:

❓ Q1 - Onde guardar o histórico?: …
➡️ Recomendo tabela própria, porque …

❓ Q2 - Quem pode apagar um item?: …
➡️ Só o autor.

Suas respostas empurram a fronteira para a frente, e ele recalcula a próxima rodada. Duas regras importam: fato é trabalho do agente (ele manda um subagente olhar o código em vez de perguntar a você) e decisão é sua. Termina quando a fronteira esvazia e você confirma que há entendimento comum.

O "with-docs" vem da segunda skill que ele carrega, a /domain-modeling: durante a conversa o agente desafia termos vagos ("conta: você quer dizer Cliente ou Usuário?"), confere se o código concorda com o que você diz, atualiza o GLOSSARY.md na hora e oferece um ADR quando uma decisão é difícil de reverter, surpreendente sem contexto e fruto de um trade-off real (os três ao mesmo tempo).

Produz
Entendimento na conversa, GLOSSARY.md e talvez docs/adr/NNNN-*.md. Ainda nenhuma spec.
2

Desvio: /prototype agente também invoca

Quando uma pergunta não se resolve no papel ("esse modelo de estados faz sentido?", "como essa tela deve ficar?"), o Matt manda fazer um protótipo descartável. São duas formas:

  • Lógica: um único arquivo HTML com botões livres e roteiros guiados que empurram a máquina de estados pelos casos difíceis, operável por quem não programa.
  • Interface: várias variações radicalmente diferentes na mesma rota, alternadas por um parâmetro na URL e uma barra flutuante.

O protótipo roda com um comando, não persiste nada e mostra o estado inteiro a cada ação. No fim, a decisão validada vai para o código real e o protótipo fica guardado numa branch prototype/<nome>, fora da main, com um ponteiro na issue. O /handoff antes e depois serve para levar o contexto a uma sessão separada (ver seção 8).

3

/to-spec você invoca

Transforma a conversa em spec. Não entrevista: só sintetiza o que já foi discutido. Por isso precisa rodar na mesma janela de contexto da entrevista. Antes de escrever, propõe as seams (as interfaces públicas onde os testes vão observar o comportamento), preferindo as que já existem e a mais alta possível, e confere com você.

O modelo da spec tem: Problema, Solução, uma lista longa de histórias de usuário ("Como <ator>, quero <recurso>, para <benefício>"), Decisões de implementação, Decisões de teste, Fora de escopo e Notas. Sem caminho de arquivo nem trecho de código, porque envelhecem rápido; a exceção é um trecho que saiu de um protótipo e diz a decisão melhor que a prosa.

Produz
Uma issue no tracker (ou .scratch/<feature>/spec.md) com o label ready-for-agent.
4

/to-tickets você invoca

Quebra a spec em tracer bullets: fatias verticais, cada uma atravessando todas as camadas (schema, API, interface, testes) por um caminho estreito, de modo que cada ticket entregue algo demonstrável sozinho e caiba numa janela de contexto nova. Fatias horizontais ("primeiro todo o banco, depois toda a API") são o que ele evita.

Cada ticket declara suas arestas de bloqueio: quais tickets precisam estar prontos antes. Ele mostra a lista numerada (título, bloqueado por, o que entrega) e pergunta se a granularidade e os bloqueios estão certos, até você aprovar.

A exceção são refatorações largas (renomear uma coluna usada em mil lugares): aí a sequência é expand → migrate → contract. Adiciona a forma nova ao lado da antiga, migra os chamadores em lotes, cada lote um ticket, e por fim remove a forma antiga.

Produz
No tracker local, um arquivo por ticket em .scratch/<feature>/issues/01-*.md; no GitHub, uma issue por ticket com bloqueio nativo entre elas.
5

/implement ou /implement-spec você invoca

/implement

Curtíssimo: implementa o que a spec ou o ticket descreve, usa /tdd nas seams combinadas, roda o typecheck e testes isolados com frequência, a suíte inteira no fim, chama /code-review e commita na branch atual. Para obra multi-sessão, roda-se um ticket por vez, com /clear entre eles.

/implement-spec

Lê os tickets como um grafo de tarefas e mantém a fronteira ocupada: um subagente implementador por ticket pronto, cada um em sua worktree, todos com /tdd. Um subagente de merge junta tudo numa branch de integração. No fim, um /code-review sobre a branch inteira e limpeza das worktrees.

O /tdd é a disciplina do código. Antes do primeiro teste, ele combina com você as seams a testar, e nenhum teste nasce fora delas. Depois, um ciclo por vez: um teste que falha, o mínimo de código para passar, e o próximo. Ele lista três antipadrões: teste acoplado à implementação (quebra ao refatorar sem mudar comportamento), teste tautológico (recalcula o esperado do mesmo jeito que o código) e fatia horizontal (todos os testes primeiro). Refatoração fica fora do ciclo e é assunto da revisão.

O /code-review compara HEAD com um ponto fixo (commit, branch, tag) em dois eixos, cada um num subagente separado para um não contaminar o outro:

  • Standards: o código segue os padrões documentados do repositório (CODING_STANDARDS.md, CONTRIBUTING.md)? Sempre somado a uma base de 12 code smells do Fowler (Feature Envy, Shotgun Surgery, Speculative Generality…), tratados como julgamento e nunca como violação dura.
  • Spec: o diff faz o que a issue pediu? Aponta o que falta, o que sobra (escopo a mais) e o que parece feito mas está errado.

Os dois relatórios aparecem lado a lado, sem reordenar um contra o outro.

6

/pr agente também invoca

Se o trabalho sobe como pull request, esta skill dá forma ao texto: um resumo como o menor visual que deixa a mudança clara, evidência de antes e depois de que funciona, e o risco do merge (porta de mão única ou de mão dupla, e o raio de impacto).

7

/retro você invoca

Olha a sessão que acabou e propõe melhorias no ambiente do agente, não no código, ordenadas por gravidade: ponteiros de navegação, checks automáticos que teriam pegado um erro, regras novas para o revisor, instruções que não mudam nada no CLAUDE.md, chamadas de ferramenta caras, informação que faltou. A regra central: erro mecânico vira check determinístico (lint, hook de pre-commit, job de CI); só julgamento vira texto em CODING_STANDARDS.md. Roda-se na própria sessão, antes do /clear.

5. Exemplo do começo ao fim

Um repositório solo, sem remote, com o tracker em markdown local. A demanda: "exportar o relatório mensal em CSV".

/setup-matt-pocock-skills      → escolhe "Local markdown"; escreve docs/agents/*
/grill-with-docs exportar relatório mensal em CSV
   rodada 1: Q1 quem exporta? Q2 quais colunas? Q3 separador?
   rodada 2: Q4 meses sem dados geram arquivo vazio ou erro? …
   → GLOSSARY.md ganha "Relatório mensal" e "Período de competência"
/to-spec                       → .scratch/exportar-csv/spec.md
/to-tickets                    → 3 tickets, o 02 e o 03 bloqueados pelo 01
/clear
/implement .scratch/exportar-csv/issues/01-gerar-csv-de-um-mes.md
/clear
/implement .scratch/exportar-csv/issues/02-botao-de-download.md
…
/retro

O que fica no repositório:

CLAUDE.md                       (bloco "## Agent skills")
GLOSSARY.md
docs/agents/issue-tracker.md
docs/agents/domain.md
.scratch/exportar-csv/
├── spec.md
└── issues/
    ├── 01-gerar-csv-de-um-mes.md     Status: ready-for-agent
    ├── 02-botao-de-download.md       Blocked by: 01
    └── 03-mes-sem-dados.md           Blocked by: 01

Repare na janela de contexto: entrevista, spec e tickets acontecem na mesma sessão, sem compactar, porque a spec é síntese da conversa. Só depois dos tickets vem o /clear, e cada /implement parte do ticket, que foi escrito para se sustentar sozinho.

6. Entradas laterais

Situações que geram trabalho e depois desembocam no fluxo principal.

/triage: pedidos e bugs se acumulando

Triagem é a primeira passada sobre o que chega de fora: um usuário abre uma issue dizendo "deu erro ao salvar" ou "seria bom exportar em PDF". Antes de alguém trabalhar nisso, um mantenedor decide se o pedido procede, se está claro o bastante e quem vai fazer. O /triage faz essa passada com você: o agente investiga e recomenda, e você decide. O resultado de cada issue é um label de estado, que diz o que acontece com ela a seguir.

Cada issue recebe uma categoria (bug ou enhancement) e um estado:

EstadoSignifica
needs-triageAinda não avaliada.
needs-infoFalta informação de quem abriu. O agente posta as perguntas e a issue volta a needs-triage quando a pessoa responde.
ready-for-agentEspecificada a ponto de um agente implementar sem você. Ganha um agent brief: comentário com o comportamento esperado e os critérios de aceite.
ready-for-humanPronta, mas precisa de gente: julgamento, acesso externo, teste manual.
wontfixNão será feita. Fecha com explicação; pedido de recurso recusado vai para .out-of-scope/, para não ser pedido de novo.
stateDiagram-v2
  direction LR
  [*] --> needs_triage
  needs_triage --> needs_info
  needs_info --> needs_triage: autor respondeu
  needs_triage --> ready_for_agent
  needs_triage --> ready_for_human
  needs_triage --> wontfix

Você pede em linguagem natural ("o que precisa da minha atenção?", "vamos ver a #42"). Para cada issue ele lê tudo, procura se aquilo já existe no código, consulta a pasta .out-of-scope/ (pedidos já recusados), reproduz o bug antes de qualquer pergunta, entrevista se faltar clareza e aplica o resultado: um agent brief para ready-for-agent, notas de triagem para needs-info, fechamento explicado para wontfix. Todo comentário começa com um aviso de que foi gerado por IA. Só vale para issues que você não criou: tickets do /to-tickets já nascem prontos. Num projeto solo, em que todas as issues são suas, ele quase não tem uso.

/diagnosing-bugs: algo quebrou

Para o bug difícil: o intermitente, a regressão entre duas versões boas. Seis fases, e a primeira é a que importa:

  1. Construir um loop de feedback: um único comando, já executado, que fica vermelho neste bug, de forma determinística, em segundos e sem humano. Sem esse comando, é proibido formular hipótese.
  2. Reproduzir e minimizar: cortar entradas e passos um por vez até que tudo o que sobrou seja necessário para falhar.
  3. Hipóteses: de 3 a 5, ranqueadas, cada uma com a previsão que a refuta, mostradas a você antes de testar.
  4. Instrumentar: uma variável por vez, logs marcados com um prefixo único ([DEBUG-a4f2]) para limpar com um grep.
  5. Corrigir com teste de regressão, escrito antes da correção, se houver uma seam correta. Se não houver, isso é o achado.
  6. Limpeza: repro original não reproduz, logs removidos, hipótese certa registrada no commit.

Depois, /retro para perguntar o que teria evitado o bug.

/wayfinder: obra grande e nebulosa

Para o que não cabe numa sessão e cujo caminho ainda não está visível (projeto novo, feature enorme). Ele planeja, não constrói. Cria um mapa (uma issue com label wayfinder:map) com Destino, Notas, Decisões até aqui, "Ainda não especificado" (a névoa) e Fora de escopo. Os filhos do mapa são tickets de decisão, perguntas cuja resposta é uma decisão, de quatro tipos:

  • research (sem você): um subagente lê fontes primárias;
  • prototype (com você): artefato tosco para reagir;
  • grilling (com você): conversa, o caso padrão;
  • task: trabalho braçal que destrava uma decisão (criar conta num serviço para avaliar a API).

A primeira sessão só desenha o mapa. Cada sessão seguinte resolve um ticket da fronteira, registra a resposta, fecha a issue e transforma em ticket a névoa que ficou nítida. Quando o caminho clareia, entra no fluxo principal pelo /to-spec.

7. O vocabulário por baixo

Duas skills de modelo são a fonte única de duas linguagens que as outras usam.

/domain-modeling: a língua do negócio

Cuida do GLOSSARY.md: um termo por entrada, definição de uma ou duas frases, e uma linha Avoid com os sinônimos proibidos. Sem nenhum detalhe de implementação. Cuida também dos ADRs em docs/adr/, que podem ter um parágrafo só.

**Pedido**:
Solicitação de compra feita por um Cliente.
_Avoid_: compra, transação

/codebase-design: a língua da arquitetura

Termos fixos: module, interface (tudo que o chamador precisa saber, não só a assinatura), depth, seam, adapter, leverage, locality. Um módulo profundo esconde muito comportamento atrás de uma interface pequena. Teste da deleção: se apagar o módulo espalha complexidade pelos chamadores, ele se pagava.

/improve-codebase-architecture você invoca usa as duas. Escolhe onde olhar pelo histórico do git (os arquivos que mais mudam), manda um subagente percorrer o código anotando atrito, e gera um relatório HTML na pasta temporária, com um cartão por candidato a "aprofundamento" (problema, solução, antes/depois em diagrama, força da recomendação). Você escolhe um, e ele entra numa entrevista sobre aquele candidato. O Matt sugere rodar a cada poucos dias.

8. Higiene de contexto

O Matt dá muito peso a quando limpar a conversa. A referência é a smart zone: cerca de 150 mil tokens nos modelos atuais, a faixa em que o modelo ainda raciocina bem. A decisão de limpar só se toma na fronteira entre fases (fim da entrevista, fim da implementação), nunca no meio delas. Na fronteira, percorra as perguntas em ordem, e a primeira resposta "sim" decide:

PerguntaSe sim
A próxima fase precisa desta conversa como fonte primária, ou ainda cabe na smart zone?Continuar. Entrevista → implementação é o caso típico.
Tudo o que está aqui é descartável para o que vem?/clear. O mais barato.
Vai trocar de ferramenta (Claude → Codex), de diretório, passar a um colega, ou desviar para uma tarefa lateral?/handoff: escreve um markdown na pasta temporária do sistema com o resumo e as skills sugeridas para a próxima sessão.
A tarefa roda sem você olhando?Subagente. Revisão automática é o exemplo.
Nenhuma das anteriores/compact com instrução do que manter. É o padrão, mas fica no fim da lista.

O motivo da ordem: todo movimento, menos continuar, troca a conversa original (fonte primária) por um resumo dela (fonte secundária), que perde informação. Limpar um contexto que ainda importava perde o porquê do que foi construído, e ler o diff depois não o recupera.

10. O que ele não cobre

Usado sozinho, o plugin cuida de uma demanda por vez, da ideia ao commit. Algumas coisas ficam de fora por desenho, e vale saber antes de depender delas:

  • Visão de produto e prioridade. Não há PRD nem roadmap. O mais perto disso é o mapa do /wayfinder, que é sobre uma obra só.
  • Fechamento da demanda. O /implement termina em revisão e commit. Não há relatório do que foi feito nem arquivamento da spec; o que fica é a issue (fechada no tracker, ou o arquivo em .scratch/), o GLOSSARY.md, os ADRs e o histórico do git. O /retro melhora o ambiente, não registra a entrega.
  • Encadeamento automático. Nenhum passo chama o seguinte. Se você esquecer o /to-tickets ou o /retro, ninguém lembra por você.
  • Verificação antes de declarar pronto. O /implement pede typecheck e suíte de testes, mas não há uma regra geral de "mostre a saída do comando antes de dizer que passou" fora do /diagnosing-bugs.

Isso combina com a proposta dele: peças pequenas que você monta, sem um processo que manda em você. O custo é que a disciplina de seguir o mapa é sua.

11. Matt e aicf lado a lado

Os dois resolvem problemas diferentes. O Matt cuida de como uma mudança sai do papel e vira código bom: entrevista, spec, fatias, TDD e revisão. O aicf cuida da governança do projeto: o que o produto é, que demandas existem, em que estado cada uma está e o registro do que foi feito. Na implementação, o aicf oferece caminhos à escolha, e o Matt é um deles. A comparação vale para mattpocock-skills 1.3.1 e aicf 0.36.0.

Matt: peças que você monta

"Não ser dono do processo." Nenhum passo chama o seguinte; você digita cada um. A disciplina mora dentro de cada passo (TDD obrigatório nas seams, revisão em dois eixos, loop de feedback antes de hipótese).

aicf: governança fixa, implementação livre

"A governança é obrigatória e sempre a mesma; a implementação é roteiro, não trilho." O registro e o fechamento não variam. Dentro da implementação, o caso decide, e sair do roteiro exige só dizer o motivo em uma linha.

Quando cada um basta

  • O Matt sozinho basta quando o que importa é a qualidade de cada entrega e o histórico do git é registro suficiente: projeto pequeno, experimento, biblioteca com issues de usuários (aí o /triage brilha).
  • O aicf faz falta quando você precisa responder, semanas depois, o que o produto é, o que está na fila, por que algo foi feito daquele jeito e o que a sessão anterior descobriu. É o registro que o Matt não guarda.

12. Os dois juntos

Instalados no mesmo projeto, o aicf fica por cima: ele decide em que fase a demanda está e a fecha, e o Matt entra como um caminho dentro das fases de entrevista e de implementação.

          GOVERNANÇA (aicf)                 CAMINHO DO MATT                    GOVERNANÇA (aicf)
intent em docs/projeto/intents/ ──▶ /grill-with-docs (entrevista) ──▶ spec em docs/projeto/specs/
                                                                            │
                                    /to-tickets  ──▶  /implement  ◀─────────┘
                                    (fatias)          (/tdd + /code-review + commit)
                                                            │
                                                            ▼
                                                  /aicf:fechar-demanda
                                       relatório, concluidas/, promoção de conhecimento

A linha Processo da demanda registra o caminho seguido, por exemplo:

Processo — entrevista: grill-with-docs · implementação: implement · issues #12, #13

Onde eles se encostam

Onde mora
Os dois respondem "onde fica o trabalho": o Matt em docs/agents/issue-tracker.md, o aicf na linha Mídia do registro do CLAUDE.md. O /aicf:setup lê o arquivo do Matt para propor o padrão, mas quem manda é a linha do aicf. Se discordarem, o agente avisa uma vez e segue a linha.
Labels
Os aicf:* marcam maturidade; os do /triage, a próxima ação. São eixos diferentes, e a mesma issue pode ter os dois.
Spec
No modo arquivo, a spec do /to-spec vai para .scratch/, que o aicf não adota. No modo issue, /aicf:criar-spec #12 adota a issue que o /to-spec criou, em vez de abrir uma segunda.
Revisão
O /implement já roda /code-review. Pela regra "exigência já satisfeita não se repete", o fechamento não deveria pedir outra revisão.
Quem digita
O agente não consegue chamar /grill-with-docs, /to-spec, /to-tickets nem /implement, porque são só do usuário. Quando o caminho escolhido é o do Matt, quem digita é você.
Em andamento no aicfEsses pontos de atrito são o assunto da spec aberta docs/projeto/specs/o-agente-nao-oferece-o-caminho-do-matt.md. A proposta: o agente conduz a entrevista pelas skills que o /grill-with-docs chama (grilling e domain-modeling, que ele pode invocar), toda spec sai pelo /aicf:criar-spec no formato do aicf, e o agente entrega a você os comandos /to-tickets e /implement já com a spec no argumento. A análise detalhada, com os riscos (reentrevistar depois do grill, perder as histórias de usuário), está na nota O Matt com e sem o aicf.
